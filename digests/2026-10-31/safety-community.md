# Community & Tools (2026-10-31)

## Key Discussions

**1. Evaluation harness token-budget bug threatens benchmark validity** — [EleutherAI/lm-evaluation-harness#4496](https://github.com/EleutherAI/lm-evaluation-harness/issues/4496) / [fix PR #4497](https://github.com/EleutherAI/lm-evaluation-harness/pull/4497) documents that `TemplateAPI.generate_until()` reserves prompt space using only `max_gen_toks`, while local completion payloads can submit a different `max_tokens`. The mismatch silently truncates prompts (a 12-token prompt could be cut to 6 tokens instead of 10), meaning published eval scores on API-backed models may have been computed on corrupted inputs. This is a quiet but consequential integrity bug for anyone citing lm-eval-harness numbers in capability or safety benchmarking.
*Why it matters: silent prompt truncation in the field's most widely used eval harness can invalidate safety/capability comparisons without anyone noticing.*

**2. NeMo Guardrails breaks on reasoning models** — [NVIDIA-NeMo/Guardrails#2539](https://github.com/NVIDIA-NeMo/Guardrails/issues/2539) reports that `IORails` unconditionally sends `temperature` and `max_tokens` to OpenAI reasoning models (e.g. o-series), which reject these params outright — causing guardrail evaluation calls to fail. Since IORails is the input/output safety-check layer, a failure here can silently disable moderation for reasoning-model deployments rather than just producing a bad completion.
*Why it matters: a guardrail library that breaks specifically when wrapping newer reasoning models is a fail-open risk exactly where oversight is most needed.*

**3. Verification layer for LLM claims has both false-positive and false-negative failure modes** — [QWED-AI/qwed-verification](https://github.com/QWED-AI/qwed-verification) logged a cluster of issues this week: `diff()` calls crash as internal errors and get reported as "proven false" ([#522](https://github.com/QWED-AI/qwed-verification/issues/522)), batch math verification returns `UNVERIFIABLE` for claims the single-item API correctly flags as proven-false ([#530](https://github.com/QWED-AI/qwed-verification/issues/530)), and the SQL verifier blocks any legitimate subquery or semicolon-in-string as malicious due to a `RecursionError` ([#529](https://github.com/QWED-AI/qwed-verification/issues/529), [#533](https://github.com/QWED-AI/qwed-verification/issues/533)). Fix PRs ([#558](https://github.com/QWED-AI/qwed-verification/pull/558), [#557](https://github.com/QWED-AI/qwed-verification/pull/557), [#555](https://github.com/QWED-AI/qwed-verification/pull/555), [#554](https://github.com/QWED-AI/qwed-verification/pull/554)) landed the same day.
*Why it matters: tools meant to formally verify agent outputs (math/SQL correctness) were themselves producing wrong admit/deny decisions — a reminder that verification layers need their own adversarial testing.*

**4. CVE-driven hardening of agent tool-call guards** — [sattyamjjain/agent-airlock#402](https://github.com/sattyamjjain/agent-airlock/pull/402) adds a guard against [CVE-2026-119050](https://nvd.nist.gov/vuln/detail/CVE-2026-119050) (CVSS 8.1–9.2), where frameworks like Agno's `PandasTools` let a model-controlled argument name an arbitrary dangerous callable for execution. The fix refuses tool arguments that reference unsafe callables and unsafe OAuth metadata URLs.
*Why it matters: shows real-world exploitability of "LLM picks the function name" patterns in agent frameworks, and that airlock-style guard libraries are becoming a necessary mitigation layer.*

**5. Coding-agent prompt-injection defenses for developer-facing agents** — [akto-api-security/akto#6885](https://github.com/akto-api-security/akto/pull/6885) adds an "Atlas" prompt-injection detection prompt specifically for endpoint-deployed coding agents (Claude Code, Cursor, Codex, Copilot, Gemini CLI), explicitly modeling the threat as *content the agent reads* (repo files, issues, MCP/tool output) rather than the developer typing malicious input.
*Why it matters: formalizes the increasingly common threat model where coding agents are compromised via indirect prompt injection from repository content, not the operator.*

## Notable GitHub Releases & Tools

- **[layered-guardrails v0.1](https://github.com/R123456-123/layered-guardrails/releases/tag/v0.1)** — First release of a layered LLM-agent guardrail pipeline (FastAPI gateway with API-key auth, rate limiting, hashed audit logging, parallel input guards for injection/PII/toxicity) plus an **ablation harness** that quantifies each layer's individual contribution to blocking rate. *Why it matters: ablation-style evaluation of guardrail stacks is rare and useful for honestly measuring defense-in-depth rather than assuming it.*

- **[guardana v1.0.2](https://github.com/guardana/guardana/releases/tag/v1.0.2)** — Fixes malformed rule/lock-file handling so scans now fail closed with specific diagnostics (exit 2/3) instead of escaping as unhandled internal errors (exit 5). Also includes [#266](https://github.com/guardana/guardana/pull/266), a pyasn1 bump closing four CVEs related to quadratic-time decoding DoS. *Why it matters: a security/compliance scanning tool tightening its own fail-closed guarantees is exactly the kind of robustness hardening that governance tooling needs before production use.*

- **[TransformerLens](https://github.com/TransformerLensOrg/TransformerLens)** — Active interpretability tooling week: a proposal for standardized **Linear Artificial Tomography (LAT) scans** to localize concept directions layer-by-layer ([#1957](https://github.com/TransformerLensOrg/TransformerLens/issues/1957)), a merged PR adding KV-group-aware destinations to direct path patching ([#1956](https://github.com/TransformerLensOrg/TransformerLens/pull/1956)), and a correctness fix for MLP weight-folding on square architectures that was silently producing incorrect activations ([#1955](https://github.com/TransformerLensOrg/TransformerLens/pull/1955)). *Why it matters: silent numerical bugs in interpretability tooling can invalidate downstream mechanistic-interpretability findings — this fix matters for anyone relying on TransformerLens activation patching results.*

- **[NVIDIA-NeMo/Guardrails — rail dependency validation](https://github.com/NVIDIA-NeMo/Guardrails/pull/2195)** — Lets rail configurations declare and validate their runtime dependencies without importing optional packages, surfacing missing-dependency failures before deployment rather than at runtime. Complemented by [speculative streaming generation](https://github.com/NVIDIA-NeMo/Guardrails/pull/2133), which runs input rails concurrently with LLM generation while buffering unreleased output-rail-checked chunks. *Why it matters: reduces a class of guardrail misconfiguration risk while improving the latency cost of output moderation, a longstanding adoption barrier for safety rails.*
