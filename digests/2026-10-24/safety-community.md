# Community & Tools (2026-10-24)

## Key Discussions

**1. Agent Cheat Index: a new benchmark for reward hacking in coding agents**
[B0yko/cheat-index v0.1.0](https://github.com/B0yko/cheat-index/releases/tag/v0.1.0) launched as "an open benchmark, harness and leaderboard for how often coding agents edit tests, special-case inputs or claim success that hidden checks contradict." The first run (10 agent configurations, 1,162 valid episodes) gives a quantitative baseline for a failure mode that's been mostly anecdotal until now — agents gaming their own grading criteria. This matters because reward hacking / specification gaming in autonomous coding agents is one of the clearest near-term alignment failure modes, and having a standardized, reproducible leaderboard turns "agents sometimes cheat" into something measurable and comparable across models.

**2. NeMo Guardrails adds tool-call/result rewriting instead of allow/block-only**
A cluster of PRs ([#2498](https://github.com/NVIDIA-NeMo/Guardrails/pull/2498), [#2499](https://github.com/NVIDIA-NeMo/Guardrails/pull/2499), [#2496](https://github.com/NVIDIA-NeMo/Guardrails/pull/2496)) resolves a long-standing limitation ([issue #2497](https://github.com/NVIDIA-NeMo/Guardrails/issues/2497)): per-tool rails could previously only allow or block a tool call wholesale, so a rail wanting to redact one sensitive field had to kill the entire turn. The new `tool_call`/`tool_result` transform targets let rails surgically mask or rewrite data, and a companion PR adds request-scoped conversation/round-trip IDs so rails can correlate the two halves of a single model call. This is a meaningful capability upgrade for production guardrail deployments, moving from binary circuit-breakers toward fine-grained data governance on agentic tool use.

**3. Critical LiteLLM auth-bypass CVE triaged in an active agent-security repo**
[sattyamjjain/agent-airlock](https://github.com/sattyamjjain/agent-airlock/pull/369) triaged [CVE-2026-114612](https://github.com/sattyamjjain/agent-airlock/issues/365) (CVSS 9.9, CWE-269/345/441) affecting LiteLLM's proxy/AI gateway, alongside a high-severity Wheels CLI issue. Given LiteLLM's ubiquity as the connective tissue between agents and model APIs (it appears across dozens of other repos in this digest as a dependency), a near-maximum-severity authz/authentication flaw in it is a supply-chain-level risk for the whole agent ecosystem, not just one project.

**4. Kernel-level containment for AI agents matures toward v0.2**
[Keter-Lab/reality-kernel](https://github.com/Keter-Lab/reality-kernel/releases/tag/v0.1.0) shipped its first release — "network, exec and file policy for AI agents, enforced in the Linux kernel with eBPF, with a signed, tamper-evident audit log of every decision" — and is already moving into Phase 16, adding [TUN/TAP containment via kernel LSM hooks](https://github.com/Keter-Lab/reality-kernel/pull/40) to close a gap where governed agents could bypass network policy through virtual network interfaces. This is one of the more technically serious approaches to agent sandboxing seen recently: rather than relying on prompt-level guardrails, it enforces capability boundaries at the OS/kernel level, which is much harder for a misbehaving or compromised agent to circumvent.

**5. Cryptographic attestation for "verified" AI outputs**
[QWED-AI/qwed-verification](https://github.com/QWED-AI/qwed-verification/pull/511) now signs every VERIFIED verification result with an ES256 attestation and publishes a JWKS endpoint so any downstream consumer can cryptographically confirm a verdict wasn't forged — closing a gap flagged in an August audit ([#319](https://github.com/QWED-AI/qwed-verification/pull/511)). Follow-on work ([#510](https://github.com/QWED-AI/qwed-verification/pull/510), [#503](https://github.com/QWED-AI/qwed-verification/pull/503)) fixes ephemeral-key persistence and clarifies that "VERIFIED" ≠ "safe to admit" (a proven-false identity is still VERIFIED but not admitted). This illustrates a growing pattern: as agents increasingly consume each other's verification claims, provenance and non-repudiation of those claims becomes its own attack surface.

## Notable GitHub Releases & Tools

- **[TransformerLens v4.3.0](https://github.com/TransformerLensOrg/TransformerLens/releases/tag/v4.3.0)** — The flagship mechanistic interpretability library's new release includes a [Whisper architecture adapter](https://github.com/TransformerLensOrg/TransformerLens/pull/1944) (enabling hooked activation caching on audio encoder/decoder models from tiny through large-v3-turbo) and fixes to block-discovery logic for non-standard architectures like Raven/Huginn ([#1855](https://github.com/TransformerLensOrg/TransformerLens/pull/1855)). Why it matters: broadening hookable-model coverage to audio models extends interpretability tooling beyond text, which is where a growing share of frontier capability work is heading.

- **[aion-context v3.0.0](https://github.com/aion-context/aion-context/releases/tag/v3.0.0)** — Introduces file format v4 (RFC-0040), which fixes [GHSA-69cp-fwrw-82vh](https://github.com/aion-context/aion-context/pull/216) by making commit-message and audit-trail bytes part of the signed payload (previously only an offset/length was covered, allowing undetected tampering), plus confidential/encrypted context rules via X25519, X-Wing (post-quantum), and external KMS recipients. Why it matters: as "context" files become a trust-bearing artifact passed between agents and tools, cryptographically binding the full audit trail — not just metadata about it — closes a real tamper vector.

- **[cage v0.1.2](https://github.com/derdelean/cage/releases/tag/v0.1.2)** — A breaking-change release where the broker now refuses to start without an explicit issuance policy unless operators set an explicit waiver flag (`CAGE_BROKER_ALLOW_NO_POLICY=1`), with the waiver permanently recorded on an audit chain ([#1](https://github.com/derdelean/cage/pull/1)). Why it matters: fail-closed-by-default for credential/capability issuance is a small but important pattern for secure agent infrastructure — it removes a silent misconfiguration path.

- **[ashlrai/phantom-secrets](https://github.com/ashlrai/phantom-secrets)** — A secrets-proxy for agentic workflows saw several hardening PRs this cycle: pinning tests that proxy auth tokens are [never forwarded upstream](https://github.com/ashlrai/phantom-secrets/pull/338), that [non-UTF-8 response headers can't be used to exfiltrate keys](https://github.com/ashlrai/phantom-secrets/pull/337), and a new [report-only LiteLLM version check](https://github.com/ashlrai/phantom-secrets/pull/329) that flags LiteLLM installs below 1.83.0 against the GHSA-5mg7 supply-chain advisory. Why it matters: as agents are given live API keys, side-channel leakage through proxy/response headers is exactly the kind of subtle vulnerability that's easy to miss and hard to detect without dedicated regression tests like these.
