# Community & Tools (2026-11-11)

## Key Discussions

**1. [agent-airlock](https://github.com/sattyamjjain/agent-airlock) becomes an MCP CVE clearinghouse amid a wave of command-injection bugs in agent tools**
A string of HIGH-severity CVEs ([CVE-2026-119025](https://github.com/sattyamjjain/agent-airlock/issues/399), [CVE-2026-117573](https://github.com/sattyamjjain/agent-airlock/issues/391), [CVE-2026-117569](https://github.com/sattyamjjain/agent-airlock/issues/390), [CVE-2026-117567](https://github.com/sattyamjjain/agent-airlock/issues/388), [CVE-2026-117561](https://github.com/sattyamjjain/agent-airlock/issues/387), [CVE-2026-117560](https://github.com/sattyamjjain/agent-airlock/issues/386)) were triaged in the same week, nearly all CWE-78 OS command injection in MCP servers (Kali-GPT, esp-mcp, sf-mcp, Gemini CLI extensions). The project's own [0.10.32](https://github.com/sattyamjjain/agent-airlock/releases/tag/v0.10.32) and [0.10.33](https://github.com/sattyamjjain/agent-airlock/releases/tag/v0.10.33) releases fixed multiple fail-open guard bugs where its own `CapabilityPolicy.require_sandbox_for` and `EvalRCEGuard` checks were never actually enforced on the real call path, only on a static scan. **Why it matters:** the MCP ecosystem is shipping shell-execution tools faster than it is securing them, and even dedicated guardrail tooling has shipped silent fail-opens — a sobering signal for anyone trusting MCP tool servers in production agents.

**2. [NVIDIA-NeMo/Guardrails](https://github.com/NVIDIA-NeMo/Guardrails) ships a batch of fail-open and payload-leak fixes in "exemplar" built-in rails**
[PR #2257](https://github.com/NVIDIA-NeMo/Guardrails/pull/2257) found that `injection_detection` **failed open** on a malformed YARA rule, and other built-in rails had manifest/payload-leak defects — found specifically by auditing the rails the project's own contribution guide holds up as best-practice examples. Separately, [PR #1967](https://github.com/NVIDIA-NeMo/Guardrails/pull/1967) fixed `mask_sensitive_data` silently ignoring the user-configured PII detection threshold due to `@lru_cache` capturing a stale default. **Why it matters:** fail-open defaults in guardrail libraries are a recurring, high-stakes failure mode — a blocked threat model that quietly becomes "allow" under edge cases undermines the entire premise of the tool.

**3. [AltairaLabs/PromptKit](https://github.com/AltairaLabs/PromptKit) HITL approval gate cannot be overridden and fails open**
[Issue #2660](https://github.com/AltairaLabs/PromptKit/issues/2660) reports that the SDK always wires in its own human-in-the-loop approval checker — an embedder cannot substitute a stricter policy — and when the checker fails to record a hold, it defaults to letting the tool execute. Related issues flag that async approval checks ([#2661](https://github.com/AltairaLabs/PromptKit/issues/2661)) don't receive context or call IDs, making identity-aware approval impossible, and that binary tool results are silently dropped across providers ([#2662](https://github.com/AltairaLabs/PromptKit/issues/2662)). **Why it matters:** HITL gates are a primary control for agentic tool-use risk; a gate that fails open or can't be customized by the embedding application defeats the safety property it's meant to provide.

**4. [TransformerLens](https://github.com/TransformerLensOrg/TransformerLens) interpretability tooling expands to SSM/hybrid architectures while hitting new API gaps**
Active interpretability work includes diffusion-LM trajectory caching and step-selective patching ([PR #2011](https://github.com/TransformerLensOrg/TransformerLens/pull/2011)), preserved provenance for pretrained J++ Jacobian lenses ([PR #2014](https://github.com/TransformerLensOrg/TransformerLens/pull/2014), [PR #2010](https://github.com/TransformerLensOrg/TransformerLens/pull/2010)), and a new MiniCPM adapter ([PR #1994](https://github.com/TransformerLensOrg/TransformerLens/pull/1994)). But [Issue #1986](https://github.com/TransformerLensOrg/TransformerLens/issues/1986) shows residual-decomposition APIs (`decompose_resid`) still raise `KeyError` on SSM and hybrid bridges (Qwen3.5, Mamba-2, NemotronH, GraniteMoeHybrid), and logit attribution was found to ignore model-specific output scaling factors, silently skewing direct logit attribution results ([PR #2013](https://github.com/TransformerLensOrg/TransformerLens/pull/2013)). **Why it matters:** as mechanistic interpretability tooling races to cover newer non-transformer architectures, subtle numerical and structural gaps can quietly corrupt attribution results researchers rely on for safety-relevant circuit analysis.

**5. [pytest-wardenbot](https://github.com/wardenbot-ai/pytest-wardenbot) adds MCP lifecycle attack scenarios and local-model-only security testing**
[v0.7.0](https://github.com/wardenbot-ai/pytest-wardenbot/releases/tag/v0.7.0) introduces an opt-in "lifecycle" attack pack covering MCP's July 2026 protocol update, including a tool-definition-swap/canary attack where a benign tool description is replaced with an injection mid-session. The preceding [v0.5.0 "trustworthy grading"](https://github.com/wardenbot-ai/pytest-wardenbot/releases/tag/v0.5.0) release explicitly notes some previously-passing tests will now fail because leak checks were rebuilt to detect actual leaked content rather than surface phrasing, and several silent grading fallbacks were made to fail loudly. **Why it matters:** this is a rare case of a testing framework publicly admitting its own grading was too lenient and fixing it — a useful model for how agent-eval tooling should handle discovered measurement flaws.
