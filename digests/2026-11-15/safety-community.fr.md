# Communauté & Outils (2026-11-15)

## Discussions clés

**1. Le mode architecte d'Aider applique automatiquement les modifications sans confirmation** — Un [signalement issu d'une revue statique](https://github.com/Aider-AI/aider/issues/5748) a révélé que `--auto-accept-architect` est défini à `True` par défaut dans la CLI, ce qui signifie que les modifications proposées par le LLM en mode architecte sont appliquées à la base de code de l'utilisateur sans passer par une validation humaine. Ceci s'ajoute à deux autres PR de sécurité d'aider fusionnées cette semaine : [la suppression des clés API dans les lignes de commande enregistrées](https://github.com/Aider-AI/aider/pull/5986) et [le retrait des caractères ANSI/de contrôle des invites de confirmation de commandes shell](https://github.com/Aider-AI/aider/pull/5981) (qui auraient autrement pu permettre à une commande proposée par un modèle de falsifier visuellement le texte de confirmation). *Pourquoi c'est important : il s'agit là d'exemples concrets où la propriété de sécurité « confirmer avant d'agir » échoue silencieusement par défaut dans un agent de codage largement utilisé — exactement le type de choix d'UX par défaut qui érode à grande échelle les garanties de supervision humaine.*

**2. Contournements du garde-fou SSRF dans le transfert de fichiers agent-à-agent (agboss)** — Un ensemble de problèmes de sécurité dans le framework d'orchestration multi-agents [agboss](https://github.com/agbossjs/agboss) montre un garde-fou SSRF contourné via un proxy d'environnement ([#916](https://github.com/agbossjs/agboss/issues/916)), via le pooling de connexions sur une requête refusée ([#1138](https://github.com/agbossjs/agboss/issues/1138)), et des spans signalant « OK » pour des requêtes qui ont en réalité échoué après un code 2xx ([#1139](https://github.com/agbossjs/agboss/issues/1139)). Les correctifs sont arrivés le jour même dans la [PR #1164](https://github.com/agbossjs/agboss/pull/1164). *Pourquoi c'est important : le SSRF dans le transport de fichiers agent-à-agent est une surface d'attaque classique pour l'IA agentique — ces découvertes montrent le nombre de vecteurs de contournement subtils (proxies, keep-alive, redirections) qu'un « garde-fou » doit réellement couvrir pour tenir.*

**3. Bugs de traversée de chemin et d'ordre de scoring dans lm-evaluation-harness d'EleutherAI** — Un [correctif de sécurité](https://github.com/EleutherAI/lm-evaluation-harness/pull/4540) ferme une directive YAML `include:` qui acceptait auparavant des chemins absolus arbitraires et des traversées de chemin, permettant aux configurations de tâches de récupérer du YAML depuis n'importe où sur le disque. Un [correctif IFEval complémentaire](https://github.com/EleutherAI/lm-evaluation-harness/pull/4616) corrige un scoring non déterministe causé par des tirages aléatoires non initialisés dans des vérificateurs intégrés. *Pourquoi c'est important : lm-eval-harness sous-tend d'innombrables chiffres publiés de benchmarks de sécurité/capacité — tant les bugs d'intégrité du système de fichiers que de déterminisme des scores menacent directement la reproductibilité des affirmations de sécurité basées sur des évaluations.*

**4. HELM constate qu'environ 10 % des questions MedMCQA ne peuvent être notées en raison de barèmes de réponses contestés** — Une nouvelle [PR HELM](https://github.com/stanford-crfm/helm/pull/4383) introduit une piste de « clés vérifiées » après avoir audité les 6 800 premières questions de MedMCQA et constaté qu'environ 1 question sur 10 ne peut pas être notée correctement — les barèmes sont contestés, les questions sont défectueuses, ou la « bonne » réponse ne figure pas parmi les options proposées. *Pourquoi c'est important : c'est un rappel que des chiffres de classement largement cités pour les LLM médicaux peuvent reposer sur des données de référence bruitées, ce qui a des implications directes pour toute affirmation de sécurité fondée sur ces benchmarks.*

**5. Les sondes de red-teaming d'Argus ciblent les agents navigateurs sur l'injection de prompt et le vol d'identifiants** — La boîte à outils de red-teaming agentique [Argus](https://github.com/gy15901580825/Argus) a livré plusieurs nouvelles sondes de navigateur cette semaine : tester si un agent outrepasse un montant de facture visible lorsqu'un texte injecté lui indique le contraire ([PR #286](https://github.com/gy15901580825/Argus/pull/286)), s'il suit une redirection de bénéficiaire injectée lors du paiement d'une facture ([PR #287](https://github.com/gy15901580825/Argus/pull/287)), et si des identifiants stockés dans le coffre-fort propre à un agent fuient vers des pages de phishing imitant des sites légitimes ([PR #293](https://github.com/gy15901580825/Argus/pull/293)). *Pourquoi c'est important : ces sondes opérationnalisent certains des scénarios de menace agentique les plus réalistes (injection de prompt causant un préjudice financier, exfiltration d'identifiants) plutôt que de tester des chaînes de jailbreak abstraites.*

## Versions et outils GitHub notables

- **[agent-airlock v0.10.35](https://github.com/sattyamjjain/agent-airlock/releases/tag/v0.10.35)** — Corrige `ShellCommandPolicy` pour vérifier *où* une commande shell écrit (cibles de redirection, actions de suppression/écriture de `find`), fermant une faille où une commande autorisée comme `echo` pouvait encore être utilisée pour écraser `/dev/sda` ou `/etc/passwd`. *Pourquoi c'est important : cela ferme une véritable voie d'escalade de privilèges dans un outil spécifiquement conçu pour isoler l'accès shell des agents.*

- **[evalproof 1.0.0–1.3.0](https://github.com/technobasant/evalproof/releases/tag/v1.0.0)** — Une vague de versions apportant une API publique stable, `evalproof scan` (analyse statique de dépôt des appels de modèles/agents/outils pour détecter les lacunes non testées), des importateurs de jeux de données pour promptfoo/DeepEval/Ragas/Inspect/etc., et une notation par juge-LLM basée sur des rubriques. *Pourquoi c'est important : cela abaisse la barrière à l'ajout d'une couverture d'évaluation systématique dans des bases de code agentiques existantes, plutôt que d'ajouter les évaluations après coup.*

- **[NVIDIA-NeMo Guardrails — correctif du contournement de injection_detection](https://github.com/NVIDIA-NeMo/Guardrails/pull/2559)** — Corrige des contournements liés à l'ordre d'occurrence dans les règles de détection d'injection Python/Jinja/XSS et ajoute une revérification de la sortie omise par rapport à toutes les règles configurées avant de laisser passer du contenu non sûr. *Pourquoi c'est important : les bugs de contournement de garde-fou sapent directement la promesse de sécurité fondamentale du produit pour les déploiements de LLM en production.*

- **[promptfoo — correctifs de pollution de prototype et de journalisation des identifiants](https://github.com/promptfoo/promptfoo/pull/12133)** — Corrige une sanitisation qui pouvait auparavant supprimer le propre champ `__proto__` d'une entrée, ainsi qu'un [correctif distinct](https://github.com/promptfoo/promptfoo/pull/12352) empêchant l'écriture brute des en-têtes `Authorization`/clés API dans les journaux d'avertissement des fournisseurs HTTP. *Pourquoi c'est important : ce sont le type de bugs d'hygiène de chaîne d'approvisionnement/de secrets qui comptent dès qu'un outil de red-teaming/d'évaluation est connecté à une CI avec de véritables identifiants.*

- **[spectral-trust 0.5.0](https://github.com/vcnoel/spectral-trust/releases/tag/v0.5.0)** — Ajoute un sous-package `interventions` apportant du patching, de l'ablation et du steering à la manière de TransformerLens au domaine de l'interprétabilité spectrale des graphes, ainsi que des visualisations animées (0.4.2) pour les traces mécanistiques. *Pourquoi c'est important : étend une boîte à outils d'interprétabilité plus légère avec des capacités d'intervention auparavant confinées à des workflows spécifiques à TransformerLens.*

- **[Argus v1.14.0](https://github.com/gy15901580825/Argus/releases/tag/v1.14.0)** — Ajoute une sonde pour les changements de description d'outil MCP en cours de session qui font fuiter les enregistrements d'autres clients, ainsi qu'une refonte de quatre sondes existantes pour noter l'attaque elle-même plutôt que le comportement ordinaire de l'agent. *Pourquoi c'est important : la mutation de description d'outil en cours de session est un vecteur d'attaque MCP sous-exploré que cette version rend désormais testable directement.*

- **[RedWidow v1.0.9](https://github.com/tomtimlt/RedWidow/releases/tag/v1.0.9)** — Première version publique d'une extension VS Code permettant aux agents IA de piloter des outils de pentest (conteneurs Kali/Exegol) avec des modes d'exécution supervisés, soumis à approbation. *Pourquoi c'est important : cela intègre directement des contrôles de supervision humaine dans un flux de travail de sécurité offensive piloté par l'IA, un modèle que d'autres projets d'outillage agentique devraient imiter.*
